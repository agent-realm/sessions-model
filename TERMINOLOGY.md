# Terminology

The vocabulary of [sessions-model](contracts/sessions-model.md) and [sessions](contracts/sessions.md), sessions-model v1.2 and sessions v1.2. Every term the two contracts use is defined here; where a definition here and a contract differ, the contract wins.

## Sessions: what a harness keeps

| Word | Meaning |
|---|---|
| **harness** | the program that runs an agent loop for a user: Claude Code, Codex, Copilot CLI, Cursor, Gemini CLI and the others. Say *test harness* for the other sense. **editor** is kept for a harness with an IDE surface (VS Code, Cursor, Zed), never as the generic word |
| **host** | the machine, as `sessions-model/host/v0` derives it from the OS machine id (or `r-` + a random id persisted per OS user, where no machine id can be read); for a service-held harness store, `s-` + an id derived from the service's domain (v1.2); never a hostname. `host_label` may travel beside it, never in a key |
| **harness_path** | the real path of the data folder a harness is bound to, or of one database file the harness keeps as a harness store of its own (every OpenCode store); absolute, symlinks resolved, in the case the filesystem stores (on a case-insensitive volume, the on-disk case the native resolver reports), never a working directory; for a service-held harness store, the service's origin (`https://claude.ai`, v1.2). With `host` and `harness` it scopes every session key; the three travel together as the JSON object `store`, which is defined only by those fields, identifies one harness store and never means a consumer's database. Replaces the retired *harness root* label (2026-10-22) |
| **harness store** | the conversation data at one `harness_path` on one host: the data folder a harness is bound to, or one such database file, including any it keeps elsewhere by override (pi `--session-dir`) or by design (Cursor IDE `agent-transcripts`); the JSON key `store` = {host, harness, harness_path} identifies it. In prose always "harness store", never bare "store", never a consumer's database. One host holds many harness stores, which is why host alone is not enough. A **service-held harness store** (v1.2) is kept by a service rather than on a machine (claude.ai's conversations, read from an export). Returned 2026-10-22, after a few hours retired |
| **session** | one conversation as one data folder on one host keeps it: `(host, harness, harness_path, session_id, incarnation)`. There is no "same session" across hosts or folders. Not a ClickHouse login session (`system.session_log`) |
| **incarnation** | one life of a session id inside one data folder: a discriminating native birth marker where the harness has one; the best weak marker (or empty) where reuse is undetectable; empty where ids are never reused. Never changed by a rewrite |
| **message** / **part** | a normalised record of one turn's message, and one block of it (text, reasoning, tool call, tool result, attachment, summary, error, notice). **Usage** is its own record, not a part. Not a chat-room message |
| **link** | how one session derives from another: `fork`, `subagent`, `rewind_copy`, `clear`, `continuation` |
| **session adapter** | the per-harness reader that emits sessions-model records; read-only toward the harness |
| **source position** | an adapter's opaque, host-local marker of how far it has read: `{kind, value}` |
| **continuity** | what a read of one source reports: `appended` (new units only), `delta` (new and changed units against the consumer's known hashes, plus gone keys), `reset` (rewritten; a new generation), `snapshot` (a whole-blob source changed) or `unchanged` |
| **removed version** | how a consumer keeps a key that left a session's `live`: the key's last row, written again at a higher `rev` and marked removed. It is never counted as live (not in totals, current-state reads or billing), it stays searchable as history, and a key that comes back is written again as current. The consumer's alternative to a tombstone ([sessions](contracts/sessions.md) §4) |
| **forget notice** | a content-free record that an admin deliberately deleted some of a session's records, or a whole session (a **forget**). The harness writes it into its harness store before it deletes anything, and keeps it for as long as the harness store exists. It carries a `forget_id`, the session's id and incarnation, the scope (the session, or every forgotten record key) and a time, and nothing else. A session adapter delivers it to a consumer that opts into the `forget-notice` feature ([sessions](contracts/sessions.md) §2, §4, §5), so the consumer can forget the same records instead of keeping removed versions. A source deletion never writes one. Always written in full: a bare *notice* is a part kind |
| **feature** | a named, opt-in addition of a v1.x to the [sessions](contracts/sessions.md) operations: optional inputs, and outputs an adapter returns only to a consumer that names the feature in `features`. Without it, an adapter behaves exactly as v1 (sessions §5). v1.1 defines one, `forget-notice` |
| **raw unit** | the smallest native piece an adapter reads (a JSONL line, a SQLite row, a blob, or several rows that one transaction must read together, such as a Devin node tree), carried in one of five encodings (`utf8`, `b64`, `row-json`, `rows-json`, `pb-json`), with every declared secret field's value replaced by the redaction marker, and the `sha256` of the bytes as emitted. Every normalised record derives from raw units ([sessions-model](contracts/sessions-model.md) §3) |
| **database profile** | one database's form of the sessions-sql mapping: the ClickHouse database profile is normative, and a Postgres database profile covers the same logical tables. Always written in full, because a bare *profile* names other things too: the sessions-only conformance profile, user and environment profiles in tooling, and ClickHouse's settings profile. Not *dialect*, which already names ClickHouse's query-language setting |
| **setup** | the harness setup a session was created under, on the session record: hashes and names only (the launch digest harness-skeleton's `hs` tool gave it, the digests of the harness's surface, the sha256 of the rendered system prompt, the tool names), and `null` unless the harness store records it, which in practice means a harness that is its own launcher (the planned `reference-harness`). Not a *profile*, and not a bare *config* |
| **seam** | the boundary a contract fixes between a provider and its consumers: [sessions](contracts/sessions.md) is the seam between session adapters and whatever reads their records |
